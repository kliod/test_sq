# SQOCH: исправленный план реализации тестового задания

**Версия:** 22.10.2026  
**Назначение:** самодостаточный план для выполнения одним разработчиком с помощью одного Codex-агента. Это инструкция для реализации, а не отчет о готовом приложении.

## 1. Что нужно сделать

Создать с нуля адаптивный React-интерфейс оформления билетов на вымышленное мероприятие **на моковых данных**. Пользователь вводит участников и контактный email, проверяет состав и стоимость, подтверждает заказ и видит либо успех, либо отказ из-за отсутствия мест непосредственно при подтверждении.

**Обязательные правила из тестового задания:**

| Правило | Как реализовать и проверить |
|---|---|
| От 1 до 4 участников | Изначально одна карточка; последнюю нельзя удалить, пятую нельзя добавить. |
| Полный тариф 2 000 ₽ | Для возраста `>= 14`. |
| Детский тариф 1 000 ₽ | Для возраста `< 14`. |
| Сопровождение ребенка | Если хотя бы один участник `< 14`, должен быть хотя бы один участник `>= 18` **в том же заказе**. |
| Поля участника | Имя и возраст для каждого. |
| Контакт | Один email для всего заказа. |
| Проверка | Видны участники, категории и **итоговая** сумма; данные можно изменить до подтверждения. |
| Два результата | Success и sold-out при попытке confirm; оба легко воспроизводимы. |
| Адаптивность | Удобная работа на desktop и при ширине экрана **360 px**. |
| Сдача | Исходники, инструкция запуска, **запись процесса**, короткая демонстрация, **фактическое время** и незавершенные пункты. |
| Защита | Короткий разбор кода и возможность внести небольшую правку при интервьюере. |

**Источник правил:** `Sqoch - Тест 1.pdf`, с. 1. Документ `SQOCH_Информация для кандидатов.pdf`, с. 1-3, описывает контекст Fullstack/AI-вакансии и критерии самостоятельности. Он **не требует** реализовывать в тесте Python, FastAPI, LLM, платежи или БД.

**Сроки:** `~60 минут` на листе задания и `15-20 минут` в FAQ - ориентиры, **не жесткие лимиты**. В README должно быть реальное измеренное время, а не число, подобранное под FAQ.

## 2. Границы и явные допущения

**Входит:** один SPA, моковое мероприятие и цены, динамическая форма участников, общая проверка сопровождения, реактивная сводка, отдельный шаг review, асинхронный mock confirm с результатами, мобильная верстка, необходимые тесты и материалы сдачи.

**Не входит:** платежная система, фактическая бронь мест, отправка email, сервер, настоящие остатки, авторизация, аналитика, БД, роутер, глобальный state manager, сохранение персональных данных в localStorage, backend/API, AI-агенты.

**Допущения, не являющиеся требованиями работодателя:**

1. Возраст вводится целым числом от нуля включительно. Значения `0` (ребенок младше года), `14`, `17`, `18` обрабатываются по исходным правилам. **Верхний предел возраста не придумывать**. Дробь, отрицательное число, пустой ввод, экспоненциальная запись и произвольный текст не принимаются.
2. Имя обязательно после обрезки пробелов; искусственные требования к длине, алфавиту и структуре ФИО не добавлять.
3. Email должен иметь базово допустимый синтаксис; пробелы по краям обрезать; уникальность, подтверждение адреса и отправку письма не имитировать.
4. Цены и пороги заданы константами. Порог тарифа **14 лет**, порог сопровождающего **18 лет**. В условии о ребенке используется именно порог `<14`. Эти правила хранить отдельно.
5. Мероприятие вымышленное; его название, дата и иллюстрация - оформление интерфейса, а не дополнительные проверки. Не требовать выбирать день, сеанс или места.
6. Успех подтверждает **демонстрационный заказ**, а не оплату или фактическую бронь. Идентификатор `DEMO-001` допустим как помеченный условный номер.
7. Sold-out определяется демонстрационным режимом; реальной емкости зала нет. Отказ возникает при асинхронном **подтверждении**, а не при вводе данных. Повторный запрос в режиме sold-out также завершается отказом.
8. При обновлении вкладки данные могут потеряться: постоянное хранение не требуется. При переходах **внутри приложения** данные теряться не должны.

## 3. Стек и контроль зависимостей

- **React + TypeScript + Vite**: базовый SPA.
- **Redux Toolkit + React Redux** (`@reduxjs/toolkit`, `react-redux`): обязательный базовый менеджер состояния приложения. Один store через `configureStore`, slice сценария через `createSlice`, `Provider` и типизированные hooks. Границы владения и сериализуемые данные — в `docs/spec/CONTRACTS.md`.
- **React Hook Form**: одна форма на весь сценарий, динамические участники через `useFieldArray`.
- **Zod** или совместимый явный валидатор: проверка строковых значений и правила присутствия взрослого. Если используется Zod, ошибку группы возвращать как ошибку массива/формы, понятную UI.
- **Стили:** один подход - Tailwind CSS **или** небольшой обычный CSS. Если Tailwind уже знаком и подключается без проблем, сохранить его. Не подключать одновременно дополнительные UI-фреймворки ради двух экранов.
- **Vitest**: тесты чистых правил и ограниченное число интеграционных проверок. React Testing Library допускается для одного критичного теста, но не обязательна, если та же функциональность убедительно проверена в браузере.
- **Без** Zustand, React Query, RTK Query, роутера, shadcn/ui по умолчанию и обязательного Playwright. Redux Toolkit обязателен; отдельный серверный кеш для mock-сервиса не нужен.

Никаких установок сторонних Codex Skills на критическом пути. Если уже настроен один проверенный дизайн-скилл, его можно использовать только для предложений по оформлению, без изменения доменных правил, архитектуры или пакетов. Возможна ручная проверка по [Web Interface Guidelines](https://github.com/vercel-labs/web-interface-guidelines), но ответственность за проверку в браузере остается у разработчика. Не исполнять непроверенные `npx`-команды или hooks исключительно ради тестового задания.

### 4.1. Типы и контракты

```ts
type ParticipantFields = { name: string; age: string };
type BookingFormValues = {
  participants: ParticipantFields[];
  email: string;
};

type Participant = { name: string; age: number };
type Booking = { participants: Participant[]; email: string };

type ConfirmResult =
  | { kind: 'success'; reference: string }
  | { kind: 'soldOut' };

type BookingService = {
  confirm(booking: Booking): Promise<ConfirmResult>;
};

type BookingStep =
  | 'editing'
  | 'review'
  | 'submitting'
  | 'success'
  | 'soldOut';
```

`ParticipantFields.age` - **строка** из HTML-поля; в `Booking.age` попадает только проверенное целое число. `ConfirmResult` - **известные бизнес-исходы**. Непредвиденный `reject` Promise - техническая ошибка, которую UI обрабатывает отдельно на экране review, без подмены sold-out.

Для динамического массива использовать **стабильный `field.id` из `useFieldArray` как React key**. Не использовать индекс массива как key и не добавлять дополнительный `participant.id` в доменную модель без необходимости. Поле email принадлежит заказу, а не участнику.

### 4.2. Правила и нормализация

Минимальные функции:

```ts
parseAge(raw: string): number | null
validateAndNormalize(values: BookingFormValues):
  | { ok: true; booking: Booking }
  | { ok: false; errors: ValidationErrors }
getTicketPrice(age: number): number
calculateTotal(participants: Participant[]): number
hasRequiredAdult(participants: Participant[]): boolean
```

`parseAge` после `trim()` принимает **только последовательность десятичных цифр**. Затем `Number(...)`; обязательно проверить `Number.isSafeInteger(age)` и `age >= 0`. Нельзя использовать `Number(raw)` без предварительной проверки, `parseInt` для частичного разбора и слепое `z.coerce.number()`: пустая строка и `13.5` иначе способны превратиться в неверный возраст.

Пример доменной логики (не требование дословно копировать код):

```ts
const FULL_TICKET_MIN_AGE = 14;
const ADULT_MIN_AGE = 18;
const CHILD_PRICE = 1000;
const FULL_PRICE = 2000;
const MIN_PARTICIPANTS = 1;
const MAX_PARTICIPANTS = 4;

const isChild = (age: number) => age < FULL_TICKET_MIN_AGE;
const isAdult = (age: number) => age >= ADULT_MIN_AGE;
const getTicketPrice = (age: number) =>
  isChild(age) ? CHILD_PRICE : FULL_PRICE;

const hasRequiredAdult = (people: Participant[]) =>
  !people.some(({ age }) => isChild(age)) ||
  people.some(({ age }) => isAdult(age));
```

На вход `calculateTotal` попадает **только нормализованный валидный** список. При ошибочных/пустых возрастах на шаге редактирования можно показывать цены отдельных **уже валидных** участников, но **не показывать неполную сумму как окончательный итог**. Рекомендуемая надпись: `Итог появится после заполнения возрастов`. При корректных возрастах сумму обновлять сразу, даже если в группе еще нарушено правило сопровождения; рядом показывать ошибку состава при попытке перехода.

Проверять:

- количество от 1 до 4;
- каждое имя после `trim()` непустое;
- каждый возраст проходит `parseAge`;
- email после `trim()` имеет допустимый базовый формат;
- если есть возраст `<14`, среди участников есть `>=18`.

Ошибки уровня конкретного участника показывать у поля; нарушение сопровождения - общим сообщением рядом с блоком участников. Запрещено продолжать к review до устранения ошибок.

### 4.3. Владение состоянием: без двух черновиков

Создать **одну** инстанцию `useForm<BookingFormValues>` в компоненте сценария `App` (или `BookingFlow`, если он единственный владелец процесса). Она **не размонтируется** при переходах, а `useFieldArray` живет на том же уровне либо в постоянном вложенном контейнере. Установить `shouldUnregister: false`, сохранить значения при скрытии полей между шагами.

- `editing`: форма и реактивная сводка получают значения через RHF (`useWatch`/`watch`), не через второй `useState`.
- `review`: после полной валидации строится **нормализованный снимок** `reviewedBooking`; сводка и сумма вычисляются только из него. На экране review нет редактируемых полей.
- `submitting`: подтверждается именно `reviewedBooking`; вся навигация и элементы изменения данных заблокированы.
- `success` / `soldOut`: хранятся статус результата и тот же подтверждавшийся снимок, чтобы не потерять состав.

Перед вызовом `confirm` заново валидировать `getValues()` и **сравнить нормализованные данные с `reviewedBooking`**. Если валидность потеряна или данные отличаются, не отправлять запрос: вернуть к редактированию или сформировать и показать обновленный review **до нового подтверждения**. Снимок не должен автоматически менять содержимое за спиной пользователя.

Состояние сценария (`step`, `reviewedBooking`, `submitError`, `reference`) хранится только в Redux Toolkit slice. Компоненты читают его через селекторы и изменяют через actions; параллельные `useState` для этих данных запрещены. RHF остается единственным владельцем редактируемых значений и ошибок полей, черновик не синхронизируется с Redux. Цена вычисляется из модели, а не хранится в store. `inFlightRef` остается локальным синхронным guard в постоянно смонтированном `App`; Promise, сервис, refs и объекты Error в store не помещаются. Асинхронный вызов выполняется вне reducer, переходы фиксируются actions. Дополнительная библиотека стейт-машины не нужна.

### 4.4. Состояния и допустимые переходы

| Исходное состояние | Событие / условие | Новое состояние | Действие |
|---|---|---|---|
| `editing` | `Продолжить`, форма валидна | `review` | Создать валидированный снимок. |
| `editing` | `Продолжить`, есть ошибки | `editing` | Показать ошибки, сфокусировать первую. |
| `review` | `Изменить` | `editing` | Не терять RHF-значения; снимок будет обновлен после новой проверки. |
| `review` | `Подтвердить`, snapshot актуален и нет запроса | `submitting` | Синхронно заблокировать повтор, вызвать mock service. |
| `review` | `Подтвердить`, данные отличаются от snapshot | `editing` или обновленный `review` | Не отправлять измененный заказ без нового показа. |
| `submitting` | `success` | `success` | Показать демонстрационный номер заказа. |
| `submitting` | `soldOut` | `soldOut` | Показать, что заказ не оформлен; сохранить данные. |
| `submitting` | неожиданный reject | `review` | Показать техническую ошибку, разрешить повтор. |
| `soldOut` | `Изменить данные` | `editing` | Сохранить все введенное. |
| `soldOut` | `Повторить проверку` | `submitting` | Без повторного создания заказа; в forced sold-out исход останется отказом. |

Не разрешать переход назад/редактирование во время `submitting`. Не показывать номер заказа в `soldOut`. После успеха можно предложить `Оформить другой заказ` с **явным сбросом формы**, но это необязательная дополнительная функция.

### 4.5. Mock BookingService и защита операции

Единый метод `confirm(booking)` возвращает Promise с небольшой задержкой. Поведение фиксируется **один раз при запуске** на основе query-параметра:

- `http://localhost:5173/` - успех;
- `http://localhost:5173/?scenario=sold-out` - отказ в момент подтверждения.

Точный локальный адрес зависит от Vite и свободного порта; README должен указывать фактический адрес и шаблон параметра. Режим определяет *исход подтверждения*, а не состав формы. До нажатия `Подтвердить` на review нельзя преждевременно показывать sold-out. По умолчанию мок детерминированен, не рандомизировать результат и не реализовывать запутанную «емкость зала».

Логическая защита нужна **помимо** `disabled` на кнопке: синхронный `inFlightRef.current`, установленный до асинхронного вызова. В `finally` снять блокировку; промежуточный результат предыдущего запроса не должен затирать новую ветку интерфейса. Поскольку во время `submitting` новые операции запрещены и повтор не отправляется, достаточно одного запроса на попытку. Для реального сервера этого мало: нужна серверная идемпотентность и отдельное решение для неопределенного результата сети, но в тесте не реализовывать.

Неожиданный reject **не равен** `soldOut`. На review показать `Не удалось проверить заказ. Попробуйте еще раз`, оставив тот же снимок и данные. Из-за мокового характера операции допустим безопасный повтор.

## 5. UI/UX: конкретный минимальный контракт

**Идея:** спокойный компактный билетный checkout, а не демонстрация возможностей UI-библиотеки. Нужна выразительная, но сдержанная визуальная иерархия.

**Экран 1 - участники и контакт:**

1. Короткая информация о вымышленном мероприятии, тарифы и правило сопровождения.
2. Карточки `Участник 1`, `Участник 2` и т.д. с именем и возрастом. У каждой дополнительной карточки - понятная кнопка удаления; после четвертой исчезает `Добавить участника`. Для последнего удаление недоступно.
3. Поле общего email после списка.
4. Сводка заказа с перечнем, стоимостью по участникам и итогом; при невалидных возрастах - честное незавершенное состояние.
5. Главная кнопка `Проверить заказ`.

**Экран 2 - проверка:** имена, возраста, тарифы, сумма, email, `Изменить` и `Подтвердить заказ`. При `submitting` показать `Проверяем наличие мест...`, индикатор ожидания и заблокированные действия. На этом экране **ничего не редактируется**.

**Экран 3 - результат:**

- **Успех:** `Тестовый заказ подтвержден`, условный номер, краткий состав и итог. Не писать `Оплата прошла` или `Билеты отправлены`.
- **Sold-out:** `Места закончились. Заказ не оформлен`. Краткое объяснение, кнопка безопасного повтора и возврат к данным. Не писать, что исправление возраста вернет места. В демонстрационном режиме forced sold-out повтор даст тот же отказ.

**Desktop:** ограниченный по ширине контейнер (ориентир 960-1100 px), два столбца на вводе: форма с большим приоритетом и сводка. **Мобильный экран 360 px:** один столбец, внешние отступы около 16 px, элементы не шире контейнера (`min-width: 0` для flex/grid), сводка перед основной кнопкой, никаких фиксированных панелей, скрывающих ввод. Обычные крупные кнопки и читаемая типографика, не более одного яркого акцентного цвета.

**Минимум доступности:**

- Явный label для имени, возраста, email; у повторяющихся полей доступное имя включает номер участника.
- Ошибки связаны с полем, например `aria-describedby`; групповая ошибка читаема и визуально близка к участникам.
- Кнопки `Добавить`, `Удалить`, `Изменить` используют `type="button"`, чтобы не запускать подтверждение формы.
- Enter на экране ввода переводит только к **валидации/review**, не отправляет booking service.
- При ошибке перехода переместить фокус к первому проблемному полю/группе; при смене экрана - к заголовку review/result. При удалении карточки фокус не должен пропадать незаметно.
- Виден `:focus-visible`, порядок Tab соответствует чтению, итог и сообщения об отправке доступны без мыши.
- Проверить на 360 px с открытой экранной клавиатурой: CTA и ошибки не перекрываются.

Не тратить время на анимации, полноэкранную бренд-систему, картинки-заглушки без смысла и визуальные эффекты, затрудняющие ввод. Конкретный дизайн оценивается в браузере, не по количеству стилистических правил.

## 8. Codex: четыре последовательные задачи для одного агента

Каждое задание выполнять **в том же репозитории последовательно**. Не запускать параллельно агентов на одних исходниках. Общие постоянные ограничения:

> Выполняй только указанную задачу и меняй только необходимые файлы. Не добавляй backend, платежи, внешние API, новые UI-библиотеки и агентские скиллы. Все доменные правила соответствуют разделу 1 этого плана. После работы запусти доступные проверки и сообщи: какие файлы изменены, что проверено фактически, что осталось непроверенным и какие компромиссы приняты. Не объявляй функцию готовой без запуска соответствующего сценария.

## 10. Вопросы для защиты

**Почему такой стек?** React/TS/Vite — базовый SPA; Redux Toolkit — выбранный пользователем базовый менеджер состояния сценария; RHF управляет динамическими полями без копии черновика в store. Чистая модель задает правила, обособленный mock определяет исход подтверждения. Backend не нужен.

**Почему два порога возраста?** От 14 лет - **полный тариф**. От 18 лет - **право сопровождать**. Это разные предикаты. Если интервьюер попросит «поднять детский тариф до 16 лет», надо уточнить, меняется ли вместе с этим правило о необходимости сопровождающего.

**Как избежать гонок?** Данные review заморожены как нормализованный снимок; перед confirm проведена сверка; in-flight guard исключает повтор в пределах одной попытки; pending запрещает редактирование. Это не подменяет серверные гарантии реального booking API.

**Где поменять тариф, лимит или правило сопровождения?** В нескольких явно названных доменных константах/функциях `bookingModel.ts` и соответствующих текстах/тестах. Не придется переписывать UI и переходы.

**Чем помог Codex?** Инкрементальная реализация и проверки по отдельным заданиям; решения о границах, состоянии, инвариантах и приемке определены автором реализации. На интервью нужно уметь объяснить каждый обработчик и воспроизвести ошибочный случай без агента.

## 11. Окончательные критерии готовности

Результат готов к сдаче, **только если одновременно**:

- реализованы все правила из раздела 1;
- success и sold-out воспроизводимы через полный путь пользователя;
- между показанным review и отправленным booking нет расхождения;
- ввод не теряется при редактировании и отказе;
- нет двойной отправки в рамках попытки;
- возрастные ошибки не превращаются в корректные тарифы;
- интерфейс работает на desktop и 360 px;
- выполнены минимальные тесты и реальные ручные сценарии;
- есть README, запись процесса, короткая демонстрация и **честное** время выполнения с перечнем незавершенного;
- разработчик способен внести небольшое изменение доменного правила при техническом разборе.

**Статус данного документа:** план готов к передаче Codex. **Статус самого приложения:** не реализовано и не проверено в рамках аудита.
