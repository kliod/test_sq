# SQOCH: требования, ограничения и источники

Источник обязательных правил — задание работодателя. Этот файл содержит применимые требования и допущения; рабочая архитектура описана в `SPEC.md` и `CONTRACTS.md`.

## Обязательные требования работодателя

| ID | Правило | Критерий приемки |
|---|---|---|
| R01 | Заказ на 1-4 участников | Нельзя оформить 0, добавить пятого или удалить последнего через UI |
| R02 | Билет от 14 лет стоит 2 000 руб. | 14 и 17 дают полный тариф |
| R03 | Билет младше 14 лет стоит 1 000 руб. | 13 дает детский тариф |
| R04 | Если есть ребенок младше 14, в том же заказе должен быть участник 18+ | 13+17 не проходит; 13+18 проходит |
| R05 | У каждого участника имя и возраст | Поля присутствуют и обязательны |
| R06 | Один общий контактный email | Поле на уровне заказа, а не каждого участника |
| R07 | Видны состав заказа и итог, можно редактировать до подтверждения | Есть сводка, проверка и возврат без потери данных |
| R08 | Нужны успех и отсутствие мест непосредственно перед подтверждением | Обе ветки воспроизводимы через полный пользовательский путь |
| R09 | Удобство на компьютере и ширине 360 px | Нет горизонтального скролла и перекрытия важных контролов |
| R10 | Передать исходники, инструкцию запуска, запись разработки и короткую демонстрацию | Реальные файлы/инструкции, доступные проверяющему |
| R11 | Указать фактическое время и незавершенные пункты; суметь сделать маленькую правку на интервью | README содержит реальные сведения; архитектура позволяет поменять правило локально |

## Явные технические допущения для реализации

Все пункты ниже - инженерные решения, **не дополнительные требования работодателя**.

- По явному решению пользователя базовый менеджер состояния приложения — **Redux Toolkit** с React Redux. Он хранит состояние сценария и нормализованный снимок заказа; React Hook Form владеет редактируемыми полями. Подробные границы — `docs/spec/CONTRACTS.md`. Это решение заменяет прежний запрет общего state manager в рабочих документах.

- Мероприятие вымышленное, без выбора даты, сеанса и конкретного места.
- Значение возраста: строка при вводе, далее целое безопасное неотрицательное число. Принимать `0`, не ограничивать верхний возраст произвольным максимумом. Запрещать пустоту, отрицательные, дробные, текст, экспоненту.
- Имя обязательно после удаления пробелов по краям; не вводить требований к кириллице или ФИО.
- Email проверять на базовую корректность формата после `trim`, без подтверждения или отправки.
- Итог не показывать как окончательный, пока хотя бы один возраст невалиден. Если возраста валидны, сумму считать независимо от ошибки сопровождения; ошибку состава показывать отдельно.
- Успех означает демонстрационное подтверждение, **не списание денег**.
- Mock-сервис асинхронный. Обычный URL дает успех, `?scenario=sold-out` дает отсутствие мест **на confirm**, а не раньше. Результат режима не случаен.
- Данные можно потерять после обновления вкладки, но нельзя терять при внутренних переходах, отказе и возврате.
- Техническая ошибка запроса не равна sold-out; предусмотреть текст ошибки и повтор без сброса формы.
- Интерфейс на русском языке, без дополнительных требований работодателя вроде входа в систему или настоящих остатков мест.

## Не делать

Сервер на Python, LLM-функции, платежи, реальную выдачу билетов, отправку писем, БД, авторизацию, роутинг, сохранение персональных данных в localStorage, дополнительный state manager помимо Redux Toolkit, дизайн-систему на десятки компонентов.

В вакансии перечислены Python/FastAPI и AI/LLM, но **это не часть данного тестового задания**.
