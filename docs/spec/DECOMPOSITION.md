# SQOCH — правила декомпозиции проекта

**Основа:** Feature-Sliced Design (FSD), подход «сначала страницы» из редакции 2.1. **Область:** организация клиентского кода в `app/src/`, границы модулей и размер задач разработки.

## 1. Статус и применение

Это инженерные правила SQOCH, подготовленные по запросу пользователя. Они дополняют [SPEC.md](SPEC.md). Продуктовые требования определены в [REQUIREMENTS.md](REQUIREMENTS.md), типы, состояния и владельцы данных — в [CONTRACTS.md](CONTRACTS.md), приемка — в [ACCEPTANCE.md](ACCEPTANCE.md).

Правила выбора ответственности и выделения модулей применяются при дальнейшей разработке. По отдельному запросу пользователя текущий код организован по схеме раздела 7. Действующие пути согласованы с `CONTRACTS.md`, [картой изменений](../change_scope_map.md) и задачами `00–06`. Структурный перенос не означает прохождение незавершенных gates; результаты проверок и handoff хранятся в kaeru.

При конфликте с продуктовым или техническим контрактом действует порядок из [WORKFLOW.md](../WORKFLOW.md). Декомпозиция сама по себе не меняет бизнес-правила, зависимости приложения или порядок gates.

## 2. Что берем из FSD

FSD организует код по трем уровням: **слой → слайс → сегмент**. Слой задает роль и направление зависимостей, слайс объединяет код по смыслу для продукта, сегмент разделяет ответственность внутри него. Например, в `pages/booking/model` слой — `pages`, слайс — `booking`, сегмент — `model`. [Описание слайсов и сегментов](https://feature-sliced.design/docs/reference/slices-segments).

В FSD 2.1 непереиспользуемая функциональность остается внутри страницы. В SQOCH ввод участников, review, ожидание и результат составляют один сценарий оформления. Отдельный экран состояния или кнопка еще не требуют собственного слайса. Это применение подхода «сначала страницы» к нашему приложению. [Объявление FSD 2.1](https://github.com/feature-sliced/documentation/discussions/756).

Слои в порядке от верхнего к нижнему:

| Слой       | Назначение                               | Применение в SQOCH                                                           |
| ---------- | ---------------------------------------- | ---------------------------------------------------------------------------- |
| `app`      | Запуск и общая сборка приложения         | Provider, store, типизированные hooks, глобальные стили, постоянный `App`    |
| `pages`    | Страницы и завершенные экраны приложения | Один слайс `booking` для оформления целиком                                  |
| `widgets`  | Крупные самостоятельные блоки            | При повторном использовании или нескольких независимых блоках страницы       |
| `features` | Значимые пользовательские действия       | При появлении действия, нужного нескольким страницам или виджетам            |
| `entities` | Понятия предметной области               | При появлении общей модели заказа или участника с независимыми потребителями |
| `shared`   | Инфраструктура и общие примитивы         | При появлении нужных нескольким модулям элементов без правил оформления      |

Создавать все слои не требуется. Слой `processes` устарел и в SQOCH не используется. Каталог проекта `app/` и слой FSD `app/src/app/` — разные уровни файловой структуры. [Определения слоев FSD](https://feature-sliced.design/docs/reference/layers).

Для текущего масштаба достаточно сборки приложения и одного модуля оформления. Наличие типов `Booking` и `Participant` не обязывает создавать `entities/booking` и `entities/participant`. Разные состояния отображения не обязывают создавать отдельные страницы.

## 3. Как выбирать границу модуля

Перед добавлением кода последовательно ответить:

1. **Какой пользовательский результат меняется?** Например: участник исправляет возраст и видит обновленную сумму.
2. **Кто владеет правилом или данными?** Найти существующий модуль в таблице раздела 4. Изменение начать у владельца.
3. **Код нужен только оформлению?** Оставить внутри `booking`, распределив по ответственности.
4. **Появился реальный второй потребитель?** Проверить, совпадают ли смысл, данные и причины изменения. Похожий JSX двух разных сценариев сам по себе не означает общую абстракцию.
5. **Что именно общее?** Примитив без бизнес-правил относится к `shared`; понятие предметной области — к `entities`; пользовательское действие — к `features`; самостоятельный блок — к `widgets`.
6. **Зависимости направлены вниз?** Если выделение требует обратного импорта, пересмотреть границу или собрать взаимодействие в общем верхнем владельце.

Выделять файл внутри модуля следует, когда у части кода есть понятная ответственность и причина меняться отдельно: например, разбор возраста, верстка участника или адаптер сервиса. Выделять новый слайс следует при собственной продуктовой ответственности и понятном публичном API.

Количество строк не служит обязательным порогом. Небольшой связный файл допустим; длинный файл с несколькими независимыми обязанностями — повод пересмотреть структуру. Не создавать прослойку, которая только переименовывает вызов и не защищает границу.

## 4. Владельцы ответственности в SQOCH

Пути в таблице — действующие пути после структурного переноса. Полные интерфейсы и переходы остаются в `CONTRACTS.md`.

| Ответственность                                                   | Владелец                                                            | Граница                                                                                       |
| ----------------------------------------------------------------- | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Редактируемые поля, ошибки ввода, динамические участники          | RHF в `app/src/app/App.tsx`                                         | Один постоянно смонтированный `useForm`; без копии черновика в Redux                          |
| Шаг, нормализованный снимок, техническая ошибка, номер результата | `app/src/pages/booking/model/bookingSlice.ts`                       | Сериализуемое состояние и допустимые переходы; без Promise, сервисов и refs                   |
| Валидация, нормализация, тарифы, сопровождение, сравнение заказов | `app/src/pages/booking/model/bookingModel.ts`                       | Чистая модель без React, Redux, DOM и сервисных вызовов                                       |
| Подтверждение и детерминированный mock                            | `app/src/pages/booking/api/bookingService.ts`                       | Получает нормализованный заказ; не управляет формой и store                                   |
| Координация проверки и подтверждения                              | `app/src/app/App.tsx`                                               | Повторная валидация, сверка снимка, локальный `inFlightRef`, вызов сервиса и dispatch         |
| Поля, сводка, review и результат                                  | `BookingPage.tsx` и четыре компонента в `app/src/pages/booking/ui/` | Отображение, локальное поведение UI и переданные обработчики; без второй версии бизнес-правил |
| Сборка store и типы всего приложения                              | `app/src/app/store/`, `app/src/app/providers/`, `main.tsx`          | Подключение reducer, Provider, корневых селекторов и типизированных hooks                     |
| Общее оформление                                                  | `app/src/app/styles/styles.css`                                     | Один основной источник стилей по `app/docs/UI_SYSTEM.md`                                      |

Цена остается вычисляемым значением. Перенос функции или компонента не дает оснований хранить сумму в store. Публичный тип импортируется у владельца; его копия в UI или сервисе не создается.

**Адаптация FSD для SQOCH:** RHF и координация единственного сценария остаются в `App`, как требует текущий контракт. Модуль оформления предоставляет модель, reducer, сервис и представление. Уменьшать `App` переносом владельца формы в другой компонент можно только после изменения соответствующего контракта отдельной задачей. FSD не является основанием для такого переноса автоматически.

## 5. Сегменты и локальные зависимости

При выделении структуры FSD внутри слайса использовать сегменты по назначению:

| Сегмент  | Что помещать в SQOCH                                                        | Что оставлять у другого владельца                         |
| -------- | --------------------------------------------------------------------------- | --------------------------------------------------------- |
| `ui`     | Компоненты оформления, доступные сообщения, локальные стили                 | Расчет тарифов и решение о допустимости заказа            |
| `model`  | Типы, чистые правила, reducer, локальные селекторы                          | Вызов `confirm`, чтение `window.location`, DOM            |
| `api`    | Контракт подтверждения, mock-адаптер, выбор режима по переданному параметру | RHF, dispatch, навигация между состояниями                |
| `lib`    | Вспомогательная библиотека с конкретной областью применения                 | Случайный набор функций из разных областей                |
| `config` | Настройки окружения или реализации модуля                                   | Тарифы и возрастные пороги, принадлежащие доменной модели |

Для SQOCH это уточнение стандартных сегментов: бизнес-константы остаются рядом с правилами. Не нужны отдельные папки `components`, `hooks`, `types`, `utils` в корне `src/`. Тип размещается рядом с владельцем; hook — рядом с поведением, которое он реализует. Пустые сегменты не создавать. [Сегменты FSD](https://feature-sliced.design/docs/reference/slices-segments).

Внутри `booking` сегменты могут взаимодействовать, но сохраняются локальные ограничения: UI использует модель; mock использует ее типы; чистая модель не использует UI или mock. Типы протокола, необходимые и reducer, и адаптеру, при необходимости выделяются в отдельный файл без побочных эффектов внутри того же слайса. Это не новый DTO и не отдельный бизнес-модуль.

## 6. Импорты и публичные API

Для структуры FSD действуют правила:

- Между слайсами разрешены импорты только на нижние слои. Слайсы одного слоя изолированы. Внутри своего слайса файлы могут обращаться друг к другу.
- В `app` и `shared` слайсов нет; их сегменты могут взаимодействовать между собой. Циклические зависимости при этом не допускаются.
- Внешний потребитель обращается через публичный API слайса. `import type` подчиняется тем же границам, что и обычный импорт.

Эти ограничения следуют [правилу импортов FSD](https://feature-sliced.design/docs/reference/layers#import-rule-on-layers).

В SQOCH публичный API нового слайса — `index.ts` с явными экспортами. Он раскрывает только нужные потребителям компоненты, типы и операции. Внутренние файлы используют прямые относительные импорты, минуя собственный `index.ts`; общий barrel для всего слоя не нужен. [Рекомендации по публичному API](https://feature-sliced.design/docs/reference/public-api).

На слоях без слайсов публичные входы задаются для экспортируемых сегментов. В `shared/ui` и `shared/lib` допустимы отдельные входы примитивов и библиотек, например `shared/ui/button`. Их внутренние файлы также скрыты от потребителей. Вход запуска `app/index.ts` служит только для подключения приложения из `main.tsx`.

Примеры для текущей структуры, из `app/src/app/App.tsx`; alias не требуется:

```ts
// Внешний потребитель — через API слайса.
import { BookingPage, bookingReducer } from "../pages/booking";
import type { BookingService } from "../pages/booking";

// Внутри booking — напрямую к своему файлу.
import { calculateTotal } from "../model/bookingModel";
```

Импорт из `pages/booking/model/bookingModel` снаружи слайса нарушает границу. Импорт из `app/store` внутри `pages/booking` направлен вверх и также нарушает ее. Эти правила действуют и для относительных путей. Alias вводится только вместе с настройкой TypeScript и Vite; сейчас используется относительный путь к публичному API.

Если двум слайсам одного слоя нужно взаимодействие, его собирает верхний модуль через props, callbacks или явные параметры. Общий код переносится вниз только при подходящей ответственности. В FSD существует специальный API `@x` для связей сущностей; в SQOCH такая связь пока не требуется. Вводить ее можно только с обоснованием в задаче, без циклов. [Исключение для сущностей](https://feature-sliced.design/docs/reference/public-api#public-api-for-cross-imports).

### Redux и направление зависимостей

В структуре FSD store собирается на слое `app`, а reducer принадлежит модулю сценария. Поэтому `app` импортирует reducer из `pages/booking`, а модуль оформления не импортирует `RootState`, store или hooks из `app`.

Селектор всего приложения, которому нужен `RootState`, размещается рядом со store. Локальный селектор сценария принимает его собственный `BookingFlowState`. Типизированные `useAppSelector` и `useAppDispatch` использует `App`; представлению передаются данные и обработчики. Выносить `RootState` в `shared` ради обхода направления зависимостей нельзя.

`selectBookingFlow` находится в `app/store/selectors.ts` и принимает `RootState`. `bookingSlice.ts` не импортирует типы или инфраструктуру `app`. Проверки, которым нужен store/Provider, находятся в `app/store/bookingIntegration.test.tsx`; `bookingSlice.test.ts` проверяет reducer без зависимости от слоя приложения.

## 7. Минимальная структура SQOCH

Ниже — действующая схема размещения. Названия существующих файлов сохраняются, `BookingPage` собирает представление из полученных данных и обработчиков. Постоянный владелец формы остается `App`.

```text
app/                               # Корень Vite-проекта
  src/
    main.tsx                       # Тонкий вход Vite, запускает app
    app/                           # Слой сборки приложения
      index.ts                     # Публичный вход для main.tsx
      App.tsx                      # RHF, guard, координация сценария
      providers/
        AppProviders.tsx           # Provider с одним store
      store/
        store.ts                   # configureStore, фабрика, корневые типы
        hooks.ts                   # useAppDispatch, useAppSelector
        selectors.ts               # Адаптация RootState к booking
        bookingIntegration.test.tsx # Связи Provider/store/страницы/сервиса через SSR
      styles/
        styles.css
    pages/
      booking/                     # Один слайс оформления
        index.ts                   # Явные экспорты для app
        ui/
          BookingPage.tsx          # Отображение текущего шага
          BookingForm.tsx
          BookingSummary.tsx
          BookingReview.tsx
          BookingResult.tsx
        model/
          bookingModel.ts
          bookingModel.test.ts
          bookingSlice.ts
          bookingSlice.test.ts
        api/
          bookingService.ts
```

`features/`, `entities/`, `widgets/` и `shared/` появятся при подтвержденной необходимости из раздела 3. В частности:

- `BookingSummary` остается локальным UI, пока показывает состав только этого оформления.
- Добавление и удаление участника остаются действиями формы; отдельные `features/add-participant` и `features/remove-participant` не нужны.
- `editing`, `review`, `submitting`, `success` и `soldOut` остаются состояниями одного сценария. Разбиение по ним не требует роутера.
- Настройка store остается в `app`, а состояние сценария — в его `model`; наличие общего store не делает всю модель глобальной инфраструктурой.

Публичный API `pages/booking` предоставляет `BookingPage`, reducer и нужные `App` функции, actions и типы. Структура внутренних компонентов остается скрытой. Все эти экспорты должны иметь конкретного потребителя; экспортировать внутренности заранее запрещено.

## 8. Как делить работу на задачи

Одна задача описывает наблюдаемый результат, основного владельца, точные пути и достаточную проверку. Сначала выбирать границу поведения, затем набор файлов. Одна задача может затронуть модель, представление и координацию, если это нужно для завершенного результата и разрешено ее scope.

| Изменение                                | Основной владелец      | Достаточная начальная проверка                            |
| ---------------------------------------- | ---------------------- | --------------------------------------------------------- |
| Правило тарифа или допустимости возраста | Чистая модель          | Граничные unit-кейсы; потребители типов при изменении API |
| Фокус после удаления участника           | Форма и ее координация | Узкая проверка удаления и фокуса в UI                     |
| Повтор после отказа                      | Сценарий подтверждения | Проверка перехода и интеграция с контролируемым сервисом  |
| Перенос файлов                           | Архитектурные границы  | Импорты, typecheck/build и проверки затронутых связей     |

Последовательность `00 → 01 → 02 → 03 → 04 → 05 → 06` сохраняется. Новые правила не объявляют пройденным незавершенный gate и не разрешают несвязанную переработку соседних модулей.

Дальнейшие структурные переходы выполняются отдельной согласованной задачей по тому же порядку:

1. Зафиксировать исходное поведение, публичные контракты и точную карту перемещений. До первых изменений приложения напомнить включить запись процесса.
2. Обновить актуальные пути в `CONTRACTS.md`, разделе архитектуры `SPEC.md`, карте изменений и затронутых задачах. Исторические материалы в `sources/` не переписывать.
3. Перенести код с сохранением одного владельца RHF, одного store и одного guard; настроить публичные API и убрать обратную зависимость от `RootState`.
4. Проверить сборку, доменную модель, reducer и измененные связи UI/Provider/сервиса по [правилам тестирования](../testing.md). Перенос владельца формы или изменение переходов требует отдельного обоснования и приемки.
5. Сохранить результат, отклонения и оставшиеся проверки в kaeru. Не создавать локальный журнал архитектурных решений.

Не совмещать такой перенос с изменением тарифов, дизайна, установкой новых библиотек или реализацией следующего этапа.

## 9. Критерии проверки декомпозиции

Изменение соответствует этим правилам, если:

- У каждого правила и изменяемого состояния один владелец; таблица раздела 4 соблюдена.
- Модуль можно назвать по его назначению, а публичный API имеет понятных потребителей.
- Код одного сценария остается связанным; нижний слой выделен по действительной потребности.
- Новые слайсы изолированы, внешние импорты идут через API, обратных и циклических зависимостей нет, включая типы.
- Чистая модель не зависит от React, Redux, DOM или сервиса; UI не дублирует правила.
- Нет пустых каталогов, общих свалок `utils/types` и копий контрактов.
- После структурного изменения данные формы, снимок, защита повторной отправки и результаты подтверждения ведут себя согласно `CONTRACTS.md` и `ACCEPTANCE.md`.
- Проверки выполнены соразмерно риску; непроверенное обозначено. Один успешный build не доказывает корректность пользовательского сценария.

Архитектурный линтер можно рассмотреть в отдельной задаче. Для применения этих правил установка новых инструментов не требуется.

## 10. Источники

Использованы первичные материалы авторов FSD, проверенные 22.10.2026:

- [FSD 2.1 — Pages come first](https://github.com/feature-sliced/documentation/discussions/756) — основание подхода «сначала страницы».
- [Layers](https://feature-sliced.design/docs/reference/layers) — назначение слоев и направление импортов.
- [Slices and segments](https://feature-sliced.design/docs/reference/slices-segments) — связность, изоляция и организация слайса.
- [Public API](https://feature-sliced.design/docs/reference/public-api) — внешние границы, явные экспорты и циклические импорты.

Выбор одного слайса оформления, сохранение RHF в `App`, размещение корневых Redux-селекторов и порядок перехода — адаптация для SQOCH с учетом действующих контрактов.
