# Проверки SQOCH: риск-ориентированная лестница

**Матрица приемки живет в `docs/spec/ACCEPTANCE.md`, а не в этом документе.** Внешний mock - заданная граница тестового задания, поэтому настоящий backend для доказательства не нужен.

## Перед тестом

```text
Измененное наблюдаемое поведение: ...
Реалистичная регрессия: ...
Минимальный достаточный вид проверки: ...
Команда/ручные шаги: ...
Когда расширять прогон: ...
```

## Лестница ширины

| Уровень | Когда применять | Пример SQOCH |
|---|---|---|
| 0: без запуска | Только план/документация, код не менялся | TASK 02: проверить наличие токенов/состояний в `UI_SYSTEM.md` |
| 1: один кейс | Одно чистое правило или исправление | `parseAge('13.5')` |
| 2: один тестовый файл | Поменялась логика `bookingModel` | `bookingModel.test.ts` |
| 3: группа в подсистеме | Поменялась связка нескольких правил/контракт | M01-M16 |
| 4: конкретная граница | Контракт `BookingService` или snapshot | Один integration тест U03/U04 с инъекцией mock |
| 5: приложение | Несколько взаимодействующих UI-переходов | editing -> review -> submitting -> result |
| 6: реальная среда | Верстка, фокус, responsive, доставка | DevTools 360 px, keyboard, старт по README |

Переход к более широкому уровню только по названному риску или явному gate. Падение сначала воспроизвести на узком кейсе. Не повторяй успешный набор, если после него не менялись соответствующие файлы/контракты. `npm run build` нужен при TS/JSX/entrypoint/поставке; он **не доказывает** корректность пользовательского пути или ширины 360 px.

## Как сопоставлять с задачами

- 00: минимальная сборка и, по возможности, запуск dev (новый entrypoint).
- 01: M01-M16 через unit, без браузерных тестов.
- 02: документарная проверка дизайн-контракта, вызов реального скилла; не повторять unit/build, если код не изменился.
- 03: U01/U02/U14/U15/U16 через узкий UI smoke или интеграционный тест при наличии; build после изменения TSX; модель повторять только при выявленной регрессии.
- 04: U03/U04/U05-U10; для гонок и подсчета вызовов надежнее один integration тест с инъекцией сервиса; остальные сценарии - браузерный smoke по возможности; build при изменении TS.
- 05: U11/U12/U17 и релевантные U14/U16 в реальном браузере, если доступен; визуальный 360 px **не заменяется** unit; сборка после JSX-поправок.
- 06: обязательный финальный `npm run test`, `npm run build` и полный вручную пройденный (или явно недоступный) контроль `docs/spec/ACCEPTANCE.md`. Итоги не подменяются фразой «проверено» без команды/среды.

## Качество тестов

- Redux Toolkit: в 03/04 узкие reducer-тесты проверяют допустимые и запрещенные переходы S02. Интеграционные U03/U04/U10 используют Provider с новым store на каждый тест (S03); проверяют поведение и payload сервиса. В 06 обязательна проверка S01-S03 из `docs/spec/ACCEPTANCE.md`.

- Проверяй наблюдаемое поведение и контракты, а не вызов приватного React-hook или внутренности библиотеки.
- Фиксируй входы, ID и тайминги; у асинхронных тестов используй управляемые Promise или fake timers, не случайные задержки.
- Не дублируй M01-M16 в E2E. E2E доказывает сквозную связку, а unit - математику и правила.
- Не добавляй test dependencies, если тот же риск надежно проверяется уже доступными средствами. Инструментальные ограничения фиксируй честно.
