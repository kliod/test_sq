# SQOCH - инструкции для Codex

Эти правила задают рабочий процесс для короткого тестового задания SQOCH. **Источником истины остается `docs/spec/`.** Работай как разработчик, который сможет объяснить и изменить собственный код на интервью.

## 1. Приоритет источников

1. Явная задача пользователя задает цель. При противоречии с требованиями безопасности или спецификацией покажи конфликт, не меняй их молча.
2. `docs/spec/SPEC.md` - полная спецификация реализации; `docs/spec/REQUIREMENTS.md` - продуктовые правила и границы обязательного задания; `docs/spec/CONTRACTS.md` - технический контракт реализации; `docs/spec/ACCEPTANCE.md` - ожидаемые результаты проверок. При конфликте между ними приоритет у исходных требований работодателя, пересказанных в `docs/spec/REQUIREMENTS.md`; расхождение зарегистрируй и запроси решение до изменения контракта.
3. `docs/spec/UX_BRIEF.md` и `docs/spec/SKILL_SETUP.md` - обязательные для UI-этапов условия в пределах предмета задачи. Внешние предложения UI/UX Pro Max никогда не меняют `docs/spec/`.
4. Корневой `AGENTS.md`, этот `docs/WORKFLOW.md`, `docs/change_scope_map.md`, `docs/testing.md` и `docs/architecture_contracts.md` - обязательный процесс: чтение, scope, проверка, отчет. При конфликте рабочих инструкций с прежним SQOCH-планом преимущество у этого процесса SQOCH.
5. `docs/tasks/NN_*.md` фиксирует цель, разрешенные пути и gate конкретной задачи. При пересечении разных модулей заранее определенные в задаче и карте scope пути разрешены; новые пути требуют отдельного согласования.
6. `app/**` показывает текущее состояние реализации, но не отменяет спецификацию. Локальные `AGENTS.md` могут уточнять работу конкретного модуля, не отменяя пункты выше.

## 2. Что читать и в каком порядке

- Всегда: этот файл, `docs/spec/SPEC.md`, `docs/spec/REQUIREMENTS.md`, `docs/spec/CONTRACTS.md`, `docs/change_scope_map.md`, текущий `docs/tasks/NN_*.md`, последний handoff из kaeru.
- При изменении поведения: соответствующие пункты `docs/spec/ACCEPTANCE.md` и `docs/testing.md`.
- При затрагивании сервисов/снимков заказа: `docs/architecture_contracts.md`.
- Для задач 02 и 05: `docs/spec/UX_BRIEF.md`, `docs/spec/SKILL_SETUP.md` и **реально установленный** локальный `SKILL.md`.
- `docs/implementation_stages.md` и `docs/templates/*` - по необходимости; не читать всю кодовую базу без причины.

## 3. Перед реализацией

1. Сформулируй наблюдаемый результат и подходящие критерии приемки, отличай требования работодателя от инженерных допущений.
2. Назови один основной модуль-владелец и точные файлы для изменения по `docs/change_scope_map.md`; соседние модули сначала только читай.
3. Исследуй актуальный код и тесты, не считай наличие документа доказательством реализации.
4. Для неочевидного изменения назови реалистичную регрессию, минимальный план и конкретные проверки до существенных правок.
5. При необходимости выйти за разрешенный scope или изменить `docs/spec/` - зафиксируй конфликт и запроси согласование. Не делай скрытый workaround.

## 4. Архитектурные инварианты SQOCH

- Приложение живет в `app/`: React + TypeScript + Vite, **Redux Toolkit + React Redux** как базовый менеджер состояния, моковый сервис подтверждения, **без** реальных платежей, Python backend, БД, AI-агентов, роутера и необязательных зависимостей.
- Единственный владелец редактируемой формы - React Hook Form на уровне `App`; нет второго изменяемого черновика.
- Единственный владелец состояния сценария — Redux Toolkit slice: шаг, нормализованный снимок, техническая ошибка и номер результата. RHF-черновик и вычисляемая цена в store не копируются; `inFlightRef` остается локальным guard в `App`.
- Возраст до валидации - строка. Нельзя превращать пустой ввод, отрицательное число, дробь или экспоненту в допустимый возраст. Порог тарифа - 14 лет, порог сопровождающего - 18 лет.
- Бизнес-решения принимает чистая модель, а не UI или mock; цена выводится из валидных возрастов, не хранится отдельно.
- На review показывается нормализованный снимок заказа; перед confirm он повторно валидируется и сверяется. `inFlightRef` синхронно блокирует вторую попытку; во время pending редактирование недоступно.
- `soldOut` и технический `reject` - разные состояния; данные не теряются. Mock-успех не выдается за оплату и настоящую бронь.
- UI/UX Pro Max используется только на 02/05 по реальному `SKILL.md`. Скилл влияет на визуальные решения, **не** на правила продукта. Установка внешних инструментов требует разрешения, выдумывать применение запрещено.

## 5. Границы и надежность

- Вноси наименьшее завершенное изменение. Запрещены несанкционированные правки других модулей, ручное дублирование контрактов, несвязанный рефакторинг и глобальное форматирование.
- Не делай git commit/push, установку глобального ПО, отправку данных в сеть и опасные команды без разрешения. Установка проектных пакетов/скилла - только после ознакомления с командой и согласования, как задано в задаче 00/02.
- Код не должен без причины менять пользовательскую семантику. Асинхронные результаты, ошибки, повторы и отмены должны иметь определенное поведение.
- Пользовательские тексты и комментарии - на современном русском. **Всегда пиши `е` вместо ее варианта с двумя точками** и длинное/среднее тире. Допустимы имена TS/API и библиотек. Прежняя формулировка «без буквы е» была ошибочной и здесь исправлена.

## 6. Проверки по риску

- Используй лестницу из `docs/testing.md`: сначала узкая релевантная проверка, затем расширение **по конкретной причине**. Не запускай весь набор тестов после каждой правки автоматически и не повторяй уже пройденное без новых затрагивающих изменений.
- Критерии gate задач остаются обязательными: модель проверяется unit, измененный сквозной сценарий - интеграционной/браузерной проверкой, TS entrypoints и финальная поставка - сборкой.
- Финальная задача 06 специально включает полный набор M01-M16, сборку и ручные сценарии. Недоступная среда не считается успешной проверкой.
- Фиксируй точные команды и результат. Не добавляй тесты ради покрытия и не дублируй одно правило на всех уровнях без отдельного риска.

## 7. Передача результата

- После каждой задачи оформи handoff по `docs/templates/HANDOFF.md` (подробная форма в `docs/templates/review_handoff.md`): наблюдаемое поведение, точные файлы, проверки и их доказательная сила, непроверенное, открытые риски, следующий шаг.
- Задачи исполняются **00 -> 01 -> 02 -> 03 -> 04 -> 05 -> 06** одним Codex последовательно. Параллелизм возможен только при явно независимых файлах, контрактах и согласованной передаче результата.
- Не переходи к следующему gate при провале предыдущего. Конфликты и явно утвержденные отклонения сохраняй в kaeru. `docs/log/spec_decisions.md` — прежний журнал, его не пополняй.
- Видеозапись процесса включает пользователь до первых изменений; Codex не подтверждает ее существование без доступа к файлу.

## 8. Хранение результатов

Фактические handoff, решения, риски и следующие шаги сохраняй в kaeru в инициативе `sqoch`. В ответе пользователю давай самодостаточный результат; локальные файлы отчетов и новую параллельную память не создавай. Шаблоны в docs/templates/ задают состав отчета. Продуктовые документы и артефакты поставки (например app/README.md) остаются в проекте. Прежний docs/log/spec_decisions.md сохранен как исторический источник и не пополняется.
