# TASK 01 - Проектирование и проверка доменной модели

> **Единый процесс:** `AGENTS.md` -> `docs/WORKFLOW.md` -> `docs/spec/` -> `docs/change_scope_map.md` -> текущая задача -> релевантный код/тесты -> `docs/testing.md` -> `docs/templates/HANDOFF.md`. Модульные границы и согласование новых путей обязательны. Не повторяй уже пройденные проверки без новой регрессии; выполни все обязательные для текущего gate проверки, а недоступные явно пометь.


**Приоритет:** P0. **Зависимость:** TASK 00. **Блок:** проектирование модели, без компонентов и стилей.

## Контекст

Прочитай `docs/spec/REQUIREMENTS.md`, `docs/spec/CONTRACTS.md`, `docs/spec/ACCEPTANCE.md` и отчет TASK 00. Пороги 14 (тариф) и 18 (сопровождение) независимы. Не путать валидный возраст с допустимостью состава группы.

## Реализация

1. Описать в `app/src/booking/bookingModel.ts` экспортируемые типы ParticipantFields, BookingFormValues, Participant, Booking, ValidationErrors, ValidationResult. Только TypeScript, без React и browser API.
2. Определить константы MIN_PARTICIPANTS=1, MAX_PARTICIPANTS=4, FULL_TICKET_MIN_AGE=14, ADULT_MIN_AGE=18, CHILD_PRICE=1000, FULL_PRICE=2000. Все правила должны использовать эти константы, а не повторяющиеся магические числа.
3. Реализовать parseAge(raw: string): number | null: после trim только ^[0-9]+$, затем safe integer и >=0. Не ограничивать возраст придуманным верхним порогом. Не допускать экспоненту, дроби, текст, минус и пустую строку.
4. Реализовать getTicketPrice, calculateTotal, hasRequiredAdult, validateAndNormalize, isSameBooking. calculateTotal принимает нормализованных участников, а не строки формы. isSameBooking сверяет email, длину, порядок, имена и возраста; простая явная реализация достаточна.
5. Для ошибок задать адресацию к имени/возрасту конкретного участника, общему email, составу группы и числу участников. При невалидном вводе не возвращать частичный Booking.
6. Email и имена нормализовать trim. Базовая проверка email достаточна; не навязывать длину ФИО, язык имени, подтверждение email.
7. Написать `bookingModel.test.ts` с M01-M16 из матрицы. Особый акцент на 13+17, 13+18, пустой возраст и границу safe integer. Для M14 можно моделировать два вызова валидатора с измененным значением, проверяя тариф, без React.

## Границы изменения

Только `app/src/booking/bookingModel.ts`, `app/src/booking/bookingModel.test.ts`, минимальные исправления `app/package.json` для тестового runner, если они действительно нужны. Не писать JSX, состояние React, BookingService, CSS или документацию дизайна.

## Gate

- Запущен целевой набор тестов модели M01-M16 (точная команда и ее результат в handoff).
- После изменения TS-типов выполнить проверку типизации/сборку `npm run build` (если она доступна); результат зафиксировать.
- Возраст представлен **строкой** до нормализации и числом только после нее.
- Цена всегда выводится из корректных возрастов; ошибка сопровождения не переписывает тариф.
- Тип ValidationResult не позволяет успешный Booking при ошибочной форме.
